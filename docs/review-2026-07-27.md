**Date**: 2026-07-27, against commit `a3a0b1d`, branch `m1-metal-tilemap-renderer`.
**Prepared by**: an independent review agent (not the authoring agent), responding to
`docs/review-brief.md`.
**Method**: code-reading review by four parallel reviewer agents (determinism/parallelism,
storage/hashing, snapshot/render/KI-001, process/CI), synthesized here. **Limitation:
the review environment had no Swift toolchain, so no gate was executed.** Every claim

---

## 1. Verdict on the framing

**The framing is right and should not be softened.** "DF-class sims are hard to verify,
not hard to write" is exactly correct for a project built by agents with a non-technical
owner: bit-exact replay is the only regression net that works without a human watching
the screen for forty hours. None of the cost is misspent. The five invariants are the
right five in substance.

The real finding of this review is different: **the guarantees are advertised as
properties of the framework, but most of them are actually properties of every future
call site — and the mechanisms that are supposed to police call sites have blind spots
precisely where the next milestone (M3, thermal simulation) will operate.** The project
is currently sound. It is not yet M3-safe. The gap is closable, and closing it before
M3 is far cheaper than after.

Second-order finding: the process failures the authoring agent confessed in the brief
(§6) are honestly reported but **two of the three have partially recurred**:
a CI probe again conflates "binary crashed" with "environment lacks GPU" (§5.1), and
implementation again ran ahead of recorded approval (M1 spec status still says
"awaiting approval" while phases 1–3 are merged, `specs/001-metal-tilemap-renderer/spec.md:3`).
Neither is severe; both mean the fix was applied to the instance, not the pattern.
The amendments in §6 target the pattern.

## 2. The five invariants — assessment

| # | Invariant | Verdict |
|---|---|---|
| I | No floats in sim state | **Keep, unchanged.** Independently validated by research; not over-applied. But see the Q16.16 range trap (§4.4) — the invariant is right, the one fractional *type* is not sufficient for M3. |
| II | Named RNG streams | **Keep, unchanged.** Design is correct; enforcement is convention-only inside parallel bodies (§3.1 hole 4), addressed via the access-declaration amendment. |
| III | Mutation only via Commands | **Keep, unchanged.** Still convention-enforced; the planned DFUI module boundary is the right structural enforcement. One hole: the pending command queue is not part of the state hash (§4.1 finding 3). |
| IV | BitwiseCopyable components | **Keep, amend enforcement notes.** ListStorage was the right workaround. Two more cliffs are visible and neither needs a new storage type — they need two rules added now: stable sub-entity IDs (positional list indices are not references), and a deterministic `SymbolID` scheme *before* the first name is generated (§4.2). |
| V | Tests + headless verb per module | **Keep, amend.** The verb exists everywhere, but "skip" currently counts as "pass" in the test harness, which is the exact failure mode this invariant exists to prevent (§5.1). Amendment: skips are counted and gated. |

**Proposed additions** (full text in §6): a sixth invariant covering serialized-state
versioning (the largest true blind spot — there is no save/load story at all, and the
replay format is "struct memory layout is the schema"), plus hardened Determinism Rules
(stencil/double-buffering, merge-is-not-conflict-resolution, wider thread counts) and
new Quality Gates (skips-are-not-passes, derived-state rule, spec-ID traceability,
recorded approvals).

## 3. Determinism and parallelism (the load-bearing claim, brief §4.1)

**The partition/merge argument is airtight for the two patterns implemented — and only
for those.** Verified sound: partition boundaries are a pure function of `(range, count)`
(`JobSystem.swift:84-102`); scratch is initialized serially, merged serially in partition
order after the barrier (`:171-190`); non-associative merges are safe because the merge
is sequential, not a tree reduction; serial and parallel paths run identical partition
lists (`:120-129, 177-185`). No completion-order leak found.

Holes, in priority order:

1. **The determinism gate never tests realistic worker counts.** Default partition count
   falls back to machine topology (`JobSystem.swift:73-75`, `CPUTopology.swift:30-33`),
   but `determinism-check` tests only `1,2,4` (`DFSimCLI/main.swift:212`). An M4 Pro
   runs 10+ workers in production paths that CI never exercises. Fix: check
   `1,2,3,7,16,64` (prime count, count > any plausible P-core count, count > small
   entity populations).
2. **Disjointness is asserted, never checked.** Every real call site goes through
   `nonisolated(unsafe)` (`JobSystem.swift:164`, `Fortress.swift:176-177`); nothing stops
   a body writing `slots[index+1]`. There is no debug-mode write-set recorder and no
   negative test proving the gate *detects* a violation.
3. **The access validator cannot see the state M3 will mutate.** `validateAccess`
   compares touched *types* against reads ∪ writes without distinguishing them
   (`TickScheduler.swift:79, 150-165`); `world.storage()` returns fully mutable storage
   regardless of declaration (`World.swift:70-84`); and `MapStore` and the RNG streams
   are entirely outside the declaration system (`Fortress.swift:64-65, 224, 241-246`).
   The flagship validation mechanism covers none of the tile state the flagship
   milestone mutates. The debug access tracker itself (`World.swift:41-43`) is a plain
   `Set` that races if `storage()` is called inside a parallel body.
4. **M3 cannot be built on the current primitives.** A temperature stencil reads
   neighbors, which requires reading tick-N while writing tick-N+1 — and there is no
   double-buffered tile field anywhere; `MapStore` is single-buffer with structurally
   side-effecting writes (`MapStore.swift:23-58`) not designed for concurrent mutation.
   M6 fluids need a third pattern ("parallel propose, serial ordered commit") that
   doesn't exist; note that "merge in partition order" on conflicting tile writes means
   *last partition wins*, which is not what a serial pass produces.
5. Doc rot that misleads the next agent: `Fortress.swift:110-111` claims per-partition
   scratch for a system that is fully serial (`runMining`, `:207-238`), and
   `Fortress.swift:202-205` claims "entity order" for what is dense (history-dependent)
   order.

**Required before the M3 spec freezes** (also in backlog): a `parallelStencil(read:write:)`
primitive over a double-buffered tile field; a deterministic active-set primitive
(collect per partition → merge in order → sort+dedupe); negative determinism tests
(in-place stencil, partition-seeded RNG, shared scratch — each must demonstrably
diverge); read/write-distinguished access declarations extended to map and RNG
resources.

## 4. Storage, hashing, numbers (brief §4.2, §4.4, invariant cliffs)

### 4.1 Hashing: the three claimed fixes verify; the story around them has four leaks

Verified correct: entity-order component hashing (`ComponentStorage.swift:195-203`),
live-lists-only ListStorage hashing (`ListStorage.swift:276-289`), MapStore uniformity
canonicalization (`MapStore.swift:216-217, 185-207`), and offset-transparent block pool
reuse (`:53-57, 202-205`).

Leaks:

1. **The hash sorts away dense order, but systems iterate in dense order**
   (`Fortress.swift:207-208`). Two states with identical hashes can differ in dense
   order and diverge on the next tick if any system's outcome is order-sensitive.
   Today's systems happen to be order-insensitive; nothing enforces it. Decide
   explicitly: either enforce "system outcomes are dense-order-independent" with a
   shuffled-storage fixture check, or hash dense order and drop the claim.
2. **Allocator free-list hashing is *correct*** (LIFO reuse means it determines the next
   `EntityID`, `Entity.swift:76-84, 108-112`) — but it makes the doc claim "identical
   fortresses by different routes hash identically" (`ComponentStorage.swift:192-194`)
   false at the `Fortress.hash` level. Scope the comments: history-independent *with
   respect to storage layout*, not entity-allocation history. Otherwise a future agent
   "fixes" one side.
3. **Pending commands are not hashed** (`Fortress.swift:277-284` vs `Command.swift:98`).
   Hash them, or document that hashes are valid only at the post-drain boundary.
4. **`Block.revision` is unhashed, history-dependent, and destined to feed path caches**
   (`MapStore.swift:38-40`). Needs the derived-state rule (§6) plus a cold-vs-warm-cache
   determinism check before any cache lands.

### 4.2 Invariant IV cliffs (brief question 2)

- **Save/load versioning: no story exists.** Only `Replay`, whose format is raw memcpy
  of structs with a hard-rejecting version field (`Replay.swift:70-71, 104-106,
  150-158`). Adding one field to `Command` invalidates every fixture with no upgrade
  path, and "save = replay the command log" does not survive worldgen. This is the
  single most expensive missing thing in the project → proposed Invariant VI.
- **StringTable/SymbolID is named in the constitution (`constitution.md:59`) but
  unimplemented.** Naive first-seen-order interning bakes allocation history into
  hashed components. Decide *before the first generated name*: content-addressed 64-bit
  IDs (hash of UTF-8, collision-checked) — which removes order-dependence entirely —
  or an append-only table treated as hashed, verbatim-serialized sim state.
- **Positional indices into ListStorage lists are not stable references**
  (`ListStorage.swift:183-188`). Add per-entity monotonic sub-IDs before anatomy/wounds.
- Item containment and historical-figure graphs: current design answers these; spec-level
  decisions only.

### 4.3 Map storage at real scale (brief question 5)

768×768×65 = 38.3M tiles ≈ **306 MB fully materialized** — survivable on unified
memory. But three things break before that:

- The compression is uniform-or-full, not palette (`MapStore.swift:42, 281-295`); one
  odd tile materializes 256. Worldgen strata veins (M4) will materialize essentially
  every solid block regardless of temperature.
- Temperature lives inside `Tile` (`Tile.swift:89`), so a thermal gradient materializes
  *structural* data. **Split temperature (and later fluids) into a separate per-block
  field store with its own uniform/materialized state** — this is a hash-affecting
  change, vastly cheaper now than after golden fixtures multiply.
- **The M3 killer is hash cost, not memory**: `MapStore.hash` walks every tile of every
  materialized block, after a full collapse scan (`:216-235`). At heavy materialization
  that is hundreds of ms per hash. Fix: per-block cached digests invalidated by a
  sim-owned dirty bit (the existing `dirty` flag at `:39` is renderer-owned and cannot
  be reused), folded in fixed block order.

### 4.4 Fixed Q16.16

- **Genuine bug**: `Fixed.rounded` uses wrapping add (`Fixed.swift:71-73`), contradicting
  the type's own trap-on-overflow contract. One-line fix.
- **Inconsistent rounding**: `*` floors toward −∞, `/` truncates toward zero
  (`:111, 122`). Deterministic but breaks negation symmetry — in a diffusion kernel,
  flux `(a−b)·k ≠ −((b−a)·k)`, which breaks conservation in ways that look like sim
  bugs three milestones later. Pick floor everywhere; test the identity.
- **Range is insufficient for temperature**: °U runs 0–60000; `Fixed(60000)` traps.
  The M3 spec must mandate the thermal kernel in scaled integers (e.g. 1/256 °U in
  `Int32` with explicit per-tile residual) or add an `Int64`-backed `Fixed64` first —
  and must resolve the `[UNKNOWN]` fractional-accumulation rule
  (`simulation-mechanics.md:24-28`), which changes observable behavior.

## 5. Render boundary, KI-001, and CI (brief §4.3, §6, question 3)

### 5.1 CI gates that can still lie

`set -euo pipefail` and loud failure are in place, and replay/determinism gates were
deliberately broken once (good). Remaining holes, each cheap to fix:

1. **Capture-gate probe recurrence of the historical bug**: `ci.sh:59-60` gates the
   capture step on `swift run dfsim scenarios` *succeeding* — so a release-only crash
   in CLI startup prints "no Metal device — capture skipped" and exits 0. Run
   `dfsim scenarios` unconditionally with `|| fail`; only the `system_profiler` Metal
   probe may skip (better: explicit `CI_ALLOW_NO_GPU=1` opt-in — the target platform
   always has a GPU).
2. **Skip-as-pass in tests**: `guard let renderer = try? TilemapRenderer() else {
   expect(true, "skipped") }` (`RenderTests.swift:196-199` and 3 more sites) conflates
   *every* init failure with "no GPU", and the harness has no skip accounting
   (`DFTesting.swift:155`). Add a counted `skip()`; init throwing must fail.
3. **Zero-fixture silent skip**: `ci.sh:30-40` exits 0 if the fixtures glob matches
   nothing. Assert `smoke.rec` exists by name.
4. **The bench gate is a gate in name only**: `--budget-ms` exists but ci.sh never
   passes it. Commit a baseline with 3× tolerance; agents read exit codes, not logs.
5. **Unregistered test suites silently never run** (`DFTests/main.swift:4-16`). Add a
   grep gate that every `register*Tests` appears in main.swift.
6. **Nothing enforces ci.sh at all**: the repo has no remote, so "merge gate" is
   agent discipline — which is the thing the gate exists to check. Push to a host with
   branch protection, or minimally a local pre-merge hook.
7. Dangling IDs: tests cite `SPEC-M0-MAP`/`SPEC-M0-SIM`, declared nowhere
   (`MapStoreTests.swift:8,42,163,232` vs `spec.md:3`); `Package.swift:4` cites a
   nonexistent `docs/ARCHITECTURE.md`. Add a mechanical traceability check.

### 5.2 Snapshot boundary

The COW-array race class is genuinely fixed (`FrameSnapshot.swift:148-198`): value-type
snapshot, single lock-guarded published slot, reader retain and writer release both
inside the critical section — no torn read possible. Residual: `@unchecked Sendable`
(`:150`) also exempts the *unenforced* single-writer convention on
`writerBuffers`/`writeIndex` from Swift 6 checking. Add a debug writer-thread assertion
and break it once. Note `FrameSnapshotRing` has no production consumer yet (only tests);
the `shot` path is single-threaded — which also means **KI-001 cannot be a ring race**.

Also: before any windowed renderer lands, the single `instanceBuffer` needs
per-frame-in-flight buffers — it is currently safe only because every caller
`waitUntilCompleted`s (`TilemapRenderer.swift:238`).

### 5.3 KI-001 — a hypothesis that survives the eliminations

The crash signature (`swift_getErrorValue` with no throw site firing) plus the decisive
anomaly — `withExtendedLifetime`, strictly safer, makes it fail *more* — points away
from memory lifetime entirely. Eliminated by code reading: there are no completion
handlers in DFRender, `waitUntilCompleted` precedes readback, all resources are
`.storageModeShared`, no weak/unowned captures.

**H1 (best fit): phantom thrown error — release codegen mishandles the Swift error
register (x21) across an inlined `rethrows` boundary.** The catch path executes with a
garbage "error box" though nothing threw. Both the failing arrangement and
`withExtendedLifetime` add `rethrows`-generic wrappers around the same code — so the
"safer" fix adding another such boundary making it fail more is exactly what this
theory predicts, and what no lifetime theory explains. Cheap discriminating
experiments, in order: (1) make `uploadInstances` non-throwing (preconditions instead
of throws at `TilemapRenderer.swift:274, 291`) — crash vanishing implicates error-path
codegen; (2) lldb `register read x21` at the trap to see what the box pointer actually
is; (3) empty `catch {}` at `main.swift:311`. **H2**: objc autorelease-return handshake
mismatch on the `MTLBuffer` existential → over-release → deterministic heap corruption;
discriminate with `NSZombieEnabled=YES` then `MallocScribble=1`. If H1 confirms, this
is an upstream compiler bug report, and the "do not re-apply withExtendedLifetime" note
in known-issues.md should be annotated with the mechanism.

### 5.4 Headless capture is weaker than advertised

"Byte-identical captures" compares two *fresh* captures against each other — no pinned
golden pixel hash exists, so a deterministic-but-wrong renderer passes forever
(`ci.sh:65-68` greps `pixelHash` but compares it to nothing). "GPU agrees with ASCII"
is binary 8×8 coverage only (`CapturedImage.swift:133-143`) at `depthLayers: 0`
(`RenderTests.swift:234`) — glyph identity, colors, depth dimming, and the multi-layer
shader path are all unexercised. Pin a golden hash; add one multi-layer capture and a
per-tile foreground-color spot check.

## 6. Proposed constitution amendments (v1.1.0)

**Status 2026-07-27: proposals only, by owner decision** (see
`docs/decisions/0001-retroactive-approvals-2026-07-27.md`) — the constitution remains
v1.0.0; an implementing agent must obtain explicit owner approval before applying
these. Fixture/save migration impact: none are
retroactive; two backlog items they mandate (temperature field split, map hash caching)
will change golden hashes when implemented and must follow the fixture-contract process.

1. **New Invariant VI — Serialized state is sectioned and versioned.** Any on-disk
   format (replay, save, fixture) consists of sections carrying a type tag, a per-type
   layout version, and a byte length; unknown sections are skippable; struct memory
   layout is never the schema without a golden layout test asserting exact bytes. A
   save is a snapshot plus command tail, not a command log. *Rationale: the current
   replay format silently makes every struct layout change a fixture-breaking event,
   and worldgen will make "replay from tick 0" unviable as a load strategy.*
2. **Determinism Rules additions**: (a) neighbor-reading (stencil) systems read a
   previous-tick buffer and write a next-tick buffer — in-place stencils are a review
   rejection; (b) partition-order merge is not conflict resolution: if two partitions
   can write the same slot, the merge must state a commutative rule or the system runs
   serially — "last partition wins" is a bug; (c) `determinism-check` must pass a
   thread set including 1, a prime, and a count exceeding the host's core count
   (`1,2,3,7,16,64`).
3. **Quality Gates additions**: (a) *skips are not passes* — skipped checks are counted
   and reported, and a skip whose precondition is not explicitly expected on the host
   fails the build; (b) *derived state may affect cost, never results* — caches and
   revision counters live outside the hash and a cold-vs-warm-cache run must produce
   identical hashes; (c) every `SPEC-*` ID cited in code exists in `specs/`
   (mechanically checked); (d) *human approvals are recorded* in `docs/decisions/`
   with date and scope — an unrecorded approval did not happen.
4. **Invariant IV enforcement additions**: `SymbolID` assignment must be deterministic
   sim state (content-addressed, or an append-only table serialized verbatim);
   positional indices into ListStorage lists are not stable references — cross-references
   use per-entity stable sub-IDs.
5. **Access-declaration scope honesty**: declarations distinguish reads from writes and
   extend to non-component resources (map, RNG streams); until they do, the
   constitution states the validator's real scope instead of implying coverage.

## 8. Answers to the brief's seven questions, in one line each

1. *Determinism argument sound?* For the two implemented patterns, yes, airtight; it
   breaks first at M3's stencil (no double-buffer primitive) and the gate never tests
   realistic worker counts.
2. *Invariant IV next cliff?* Save/load versioning (no story at all) and string
   interning (named in the constitution, unimplemented, easy to build wrong); amend now
   (§6.1, §6.4).
3. *KI-001?* Yes — phantom-error/rethrows codegen (H1) uniquely explains the
   `withExtendedLifetime` anomaly; three cheap discriminators listed (§5.3).
4. *Milestone order right?* Keep temperature at M3, but the evidence is one wiki source
   family — de-risk with a measured prototype benchmark before freezing the M3 budget,
   and record the reorder as a human-approved decision.
5. *Palette map viable under temperature?* Not as-is — split the thermal field out of
   `Tile` and make map hashing incremental; memory survives, hash cost does not.
6. *Missing entirely?* Save versioning (worst), string interning, conflict-resolution
   semantics for fluids, branch protection, decision log, golden pixel baseline.
7. *(Implied) are the remaining guards proven?* No — the access validator, the GPU-test
   skip path, and the snapshot single-writer convention have never been shown to fire.
